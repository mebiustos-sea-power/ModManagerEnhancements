# ゲーム本体のファイル読込仕様に基づく重複判定の調査

- 調査日・追加調査日: 2026-11-03（日本時間）
- 対象MOD: Mod Manager Enhancements v0.1.13
- 対象ソース: `048581b1ac91adedff78331a75033b65c475d0b6`
- 調査範囲: ゲーム本体のファイル検索・読込範囲と、MOD間のファイル重複判定への影響

## 結論

**目的はファイル単位の重複と提供順位を確認することである。ゲーム本体の読込仕様を根拠に、同じ相対パスのファイルが同じ対象を上書きするのか、別々の入力になるのかを区別する。**

モデル・材質・地形の主要な経路を追加調査した。主な結果は次のとおり。

1. **外部OBJ、材質定義、そこから参照される画像には、通常のMOD優先順位で検索される経路がある。** 同じ検索パスへの提供ファイルは、従来の相対パス・内容比較を利用できる。
2. **Unity内蔵リソースと外部ファイルは同じものではない。** 拡張子のないリソース名に対し、同名のOBJやPNGを自動的に補って検索する規則ではない。
3. **OBJの `mtllib` は読み飛ばされる。** 一般的なOBJ形式の知識だけでMTLと画像の読込関係を付け足すと、ゲームの動作とずれる。
4. **地形には固定ルートやミッションの実パスに付随する入力がある。** すべてを「有効MODの一覧で最初のファイルが優先」とする判定は適切ではない。
5. **実行時の使用状況の完全再現は、このMODの必須要件にしない。** モデル内部の子要素、描画結果、INIキー単位の競合まで追う必要はない。今回の調査で見つかった条件分岐は、ファイル検索規則の根拠として記録する。

最終的に採用した判定は次の3つである。

1. ゲーム本体の仕様で上書きになると確認できるものは、従来の条件で重複扱いにする。
2. ゲーム本体の仕様で独立した入力になると確認できるものは、重複扱いにしない。
3. どちらとも判断できないものは、従来の条件で重複扱いにする。

**現行の相対パス比較は基本として妥当である。ミッション全般の判定不良や大規模な方式変更が必要という結論にはしない。** 調査の発端となったMOD直下の `preview.jpg` はWorkshop用画像であり、従来どおりの重複扱いが正しい。

今回実装した補正は、独立した背景候補として読み込まれる **`ui/backgrounds` 直下のPNGのみ**を対象外にするものとなる。サブフォルダ、他形式、`preview.jpg`、独自DLL用JSON等は従来の判定を維持する。以下の詳細調査は読込規則の根拠であり、その全経路を再現する実装要件ではない。

## 目的と範囲の再確認

ユーザーが明示した条件を、実装方針の前提とする。

- 確認するのは、MODに含まれる**ファイルの重複**である。
- ゲーム本体の読込仕様によって、同じパスが同じ対象になるか、一覧の優先順位が適用されるかを確認する。
- **DLL独自のI/Oは調査しない。その用途のJSON等は、通常の相対パスの重複として扱ってよい。** 独自DLL専用データを判別したり、実際にDLLが使用するかを確かめたりする必要はない。
- 別名のファイルが同じ描画用途に使われることだけでは、ファイル重複とはしない。
- INIの異なるキー・セクションが共存することと、同じパスのファイルが複数提供されることを区別する。キー単位の競合解析は今回の目的に含めない。

前段の再調査では「ゲームの読み込み要求の生成」を中心に据えすぎ、全カタログや有効な設定値から実際の使用リソースを再現することまで、必須に近い扱いにしていた。今回の補足に基づき、その部分を修正した。読み込み要求の追跡は**比較単位と検索範囲を確かめる調査手段**であり、全リソースの実行時依存グラフを作ることが製品要件ではない。

未知のデータを一律に無視する設計にも変えない。DLL固有データを含む通常の相対パス比較を基礎にし、ゲーム本体について確認できた読込範囲・優先規則を反映する。特定のファイル名を見つけるたびに除外条件を追加する方式を、基本設計にはしない。

## ファイル比較に必要な読込規則

| 規則 | 確認した例 | 重複判定への意味 |
| --- | --- | --- |
| 共通の相対パス検索 | ミッションINI、外部OBJ、外部画像 | 同じ相対パスの提供元を集め、管理画面の有効状態と優先順位を使う |
| 所有元・実パスを基準に読む | 各MODの `_info.ini`、ミッション隣の `_data` | 別MODの同名ファイルを、無条件に同じ上書きグループにしない |
| 各実ファイルを独立した候補として列挙 | メニュー背景画像 | 同じ相対パスでも候補として共存する経路があり、最上位の1件への置換と断定しない |
| 固定ルートから選択 | 地形DEM、設定依存のAssetBundle経路 | 通常MODの並び順を、そのまま優先順位として適用しない |
| Unity内蔵リソースの検索 | 拡張子のないモデル名、一部の地形テクスチャ | StreamingAssetsに同名ファイルがあるだけでは、通常の上書き提供元にならない |
| 複数入力の合成 | INI拡張・仮想ローカライズ | ファイルの重複は比較できるが、下位ファイル全体が失われるという説明は避ける |

未知の独自データについては、通常の相対パス比較を許容する。本体で特殊な規則が確認できた入力と、独自DLLの読込仕様が不明なデータを、同じ理由で扱い変更しない。

## 前段で確認したミッション・画像・INI

### ミッションとMOD直下のpreview.jpg

`ScenarioMenuViewModel.GetMissions` は、フォルダをたどり、`GetFiles(folder, "*.ini")` で得た相対パスを `GetFile` で解決する [R07]。`_data`・`_briefing`・`_temp` のフォルダや `_info.ini` には、ゲーム自身の列挙規則がある。

実ファイルの読み取りサンプルでは、次のミッション定義は別々の検索パスになった。

| 相対パス | この2MOD内の提供元数 |
| --- | --- |
| `missions/Tsushima Dawn/Tsushima Dawn - Blue.ini` | 1 |
| `missions/Tsugaru Gauntlet/Tsugaru Gauntlet - Blue.ini` | 1 |

両MOD直下に内容の異なる `preview.jpg` が存在する。ユーザーの確認により、これはWorkshop用画像と分かった。通常のミッションエントリの列挙はその画像を要求しないが、ゲームでの用途の有無は、従来のファイル重複から外す理由にはしない。**この検出をバグ・誤判定とした以前の判断は訂正する。**

ミッション固有フォルダが異なる上記2つのINIは、現行スキャナでも異なる相対パスとして区別される。提示された構成から、ミッションの重複判定に問題があるとは言えない。

### プロフィールと背景

- `UnitMetadataProvider.GetIniNames` はユニットのINIカタログを生成する [R08]。
- `IniToProfileConverter.LoadUnitArt` は、コピー元ごとに番号付き画像、標準画像を検索する [R09]。**別名の代替画像同士を、それだけでファイル重複にまとめない。**
- 保存済み構成を使った標準プロフィールの限定サンプルでは、`jasdf_f-15j_peaceeagle.png`、`jp_f-2a.png`、`jp_f-2a_late.png` の同一相対パスに異なるMOD内容が残った。通常MODの順序を反転した計算では、3件とも最初の提供元が切り替わった。
- メニュー背景は `GetAllFiles("ui/backgrounds", "*.png")` で各実パスを集め、その中から選んだ実パスを画像ローダーに渡す [R10・R11・R12]。この経路で共存する入力を、一律に1つの勝者・敗者へ変換しない。

これらのサンプルは、ゲームのメソッドを実行したものではない。

### INIとローカライズ

`IniHandler.open` には、基本ファイルの検索に加え、extend/prepend/copy/alias等の処理がある [R14]。`LocalizationLoader.OpenVirtualLocalizationFile` は複数ルートのINI/JSONや追加ディレクトリの入力を合成する [R13]。

ファイル重複の表示に、これらのキー単位の最終結果まで求めない。同じパスのファイルが複数あることと、どのキーが失われるかは別の情報である。異なる名前の合成入力を、同じ用途という理由だけで重複ファイルにまとめることもしない。

`IniHandler.ReadFileToIni` は非公開のインスタンスメソッドで、型初期化やインスタンス状態への依存がある [R15・R19]。しかし、**この目的のために独立した完全互換パーサーを作ることは、現時点の必須要件ではない。** ファイルの提供順位を示す場合は、合成があり得ることを説明する従来の方針を基礎にできる。

## 追加調査: モデルの読み込み

### ユニット定義からのパス生成

`ObjectBaseLoader.BuildModelHierarchy` は、ユニットINIの `[Models]` にある `ResourcesFolder` と `ResourcesRoot` を連結し、`ResourceLoader.getGameObjectResource` に渡す [R20]。

サブモデルは `[Submodels]` があればその各値を使い、なければ `[Models]` の `NumberOfSubModels` と `SubModelN` を使う。各サブモデルの `ResourcesMeshFolder`、`RootMesh`、`Mesh`、材質関連の値を読む [R20・R21]。

### 外部ファイルと内蔵リソースの分岐

`getGameObjectResource` とその外部ファイル読込部で確認した規則 [R22]:

| 指定 | 処理 | ファイル比較への意味 |
| --- | --- | --- |
| 拡張子付きの `.obj` | `FileManager.GetFile` で選んだ実パスをOBJローダーへ渡す | 同じ相対パスのOBJは、通常の有効状態・MOD優先順位で比較できる |
| 拡張子付きの `.ini` | 選んだ実パスをINIとして読み、`ParticleSystemFactory` で生成する | この分岐はパーティクル定義。通常のモデルファイルと同じ意味のINIとは限らない |
| 上記の外部読込がnullを返した場合 | 拡張子を取り除いたリソース名で `Resources.Load<GameObject>` | Unity内蔵側への代替検索。例外時の処理とは区別する |
| 拡張子のないリソース名 | 外部OBJ/INI読込へは進まず、Unity内蔵側を検索 | 同名の `.obj` を自動補完する規則ではない |

確認した外部モデル読込部には、FBX・glTFをファイルから取り込む分岐はない。これは今回確認したローダーについての事実であり、拡張子だけで全経路のファイルを禁止・除外する根拠にはしない。

### OBJのMTL参照

収録されている `Dummiesman.OBJLoader.Load(Stream, bool)` は、`mtllib` 行で `SkipUntilNewLine` を呼び、その行を読み飛ばす [R23]。この経路からMTLファイルの追加読込は発生しない。

したがって、一般的なOBJ形式を根拠に「同梱MTLが同名なので材質が上書きされる」と判断するのは適切ではない。別の本体読込経路で同じファイルが明示的に参照される場合は、その経路の規則で扱う。

### 代替モデルの条件を調べた理由と限界

`createObjectPartObject` には、選択したルートモデル内にメッシュが見つからない場合に、代替フォルダのモデルを検索する分岐がある。LODや損傷モデル用の名前も生成する [R20]。

これは、同じ用途のモデルをすべて同列の提供元にまとめてよいわけではない、という根拠になる。ただし、**ファイル重複の検出のために、Unity内のモデルをロードして子要素の有無まで判定する機能は要求しない。** 特定のファイルが実行時に必ず使用されるという保証を、重複表示に付け加えない。

## 追加調査: 材質・画像・パーティクル

`ResourceLoader.getMaterialResource` の外部読込部は、拡張子があり、ファイルが存在する場合、その指定を `Utils.openIniFile` に渡して材質を生成する [R24]。外部材質はUnityのシリアライズ済み `.mat` をそのままインポートする処理ではなく、この経路ではINIとして評価される。拡張子のない指定には `.ini` を自動付加しない。

| 入力 | 読込処理 | 比較への反映 |
| --- | --- | --- |
| 外部材質定義 | `getMaterialResource` → INI読込 | 同じ相対パスの定義を比較する。INI合成への注意は共通 |
| 材質INIの `[Textures]` の値 | `getTexture2dResource` → `LoadTextureFromFile` | 値のパスを使う。材質INIの親フォルダを自動的に付ける処理ではない |
| サブモデルの `MaterialTextureDiffuse/Specular/Normal` | 指定された材質用フォルダと値を組み合わせ、`getTextureResource` | 生成された相対パスへの提供ファイルを比較する |
| `[Shader] Path` | `Shader.Find` | 外部の同名 `.shader` を通常MODの検索順で読む処理ではない |
| パーティクルのRenderer材質 | `getMaterialResource` | 同じ材質検索規則を使う |
| パーティクルのSubEmitter | 定義パスを `GetFile` で解決してINI読込 | 本体で確認できた共通検索の経路 |

根拠は [R20・R24・R25・R26・R28]。相対パスの外部画像は通常の検索、絶対パスの画像はそのファイルを読むという区別も維持される [R12]。

### 実在する材質参照の読み取りサンプル

Workshop item `3373960386` の `vessels/usn_cv_forrestal_75.ini` にある `[Submodels]` と `[Forklift]`、参照先の材質定義を読んだ。

| 種類 | 定義から得たパス |
| --- | --- |
| 条件付きの代替OBJ | `ships/equipment/usn_forklift.obj` |
| 材質INI | `ships/materials/usn_forklift.ini` |
| `_MainTex` | `ships/materials/usn_forklift_tx.png` |
| `_SpecTex` | `ships/materials/usn_forklift_spec.png` |
| `_BumpMap` | `ships/materials/base_nm.png` |

5つの実ファイルが存在することを確認した。Shader名は `Marmoset/Bumped Specular IBL` で、通常ファイルの検索パスとは別である。

これは**実ファイルにある記述と参照先の存在確認**であり、ゲームのパーサー、設定合成、Unityのモデル検索を実行したものではない。OBJについては代替読込の条件を記録し、実行時の使用や、現在の有効構成での優先提供元までは主張しない。

### プリローダーの扱い

`UnitAssetPreloader.CollectUnitAssets` は、モデル・材質・テクスチャ・一部のエフェクト等の参照を集める [R27]。モデル参照項目を整理する調査資料として利用できる。

一方、プリロード用に集めた名前のすべてが、その場面の最終的な描画に使われるとは限らない。ファイル重複チェックのために、プリローダーの全処理やミッションのユニット生成を再実装する必要はない。`IniPreloader` も同様に、全リソースの利用状況を確定する機構とは扱わない [R16]。

## 追加調査: 地形・配置物

### 地形データとミッション付随ファイル

| 経路 | 確認した規則 | 比較への意味 |
| --- | --- | --- |
| 地形DEMルート | `TerrainManager.OnStart` は `user/terrain/data/y1_x01.lz4` があればuser側、なければoriginal側を選ぶ | 各タイルについて通常MOD一覧から最上位を探す方式ではない |
| DEMの名前生成 | `getDEMFileName(x, y)` のキーに `.lz4`、`-splat.lz4`、`-splat2.lz4` 等を付け、選んだ実ルートを読む | ルートの選択と同一パスのMOD優先順位を混同しない |
| ミッションの地形編集 | `currentMissionFilePath` の親とファイル名から `<mission>_data/chunk_x_y.dat`、`chunkSplat_x_y.dat` を作り、実パスを読む | ミッションの採用元と付随フォルダを基準にする。別MODの同名付随ファイルが共通検索で入れ替わるとは限らない |
| ルート側の地形編集 | ミッション側の編集に加え、worldPathの `chunk_x_y.dat` 等を適用する | 単一ファイルへの置換だけではなく、複数段階の入力がある |
| 追加の編集マスク | `TerrainChunk` コンストラクターにはoriginal側の `chunkVegMask_x_y.dat` 等を直接読む部分がある | ここにも通常MODの全ルート検索を仮定しない |

根拠は [R31・R32・R33]。`Utils.OpenFile` は存在確認後に指定されたファイルを開き、独自にMOD一覧を検索し直す処理ではない [R40]。

`LoadDEMUncompressed` というRAW読込メソッドもあるが、今回の参照索引では直接の呼び出し元を確認できなかった。確認した `LoadDEMCore` は圧縮データの読込を呼び、必要な圧縮ファイルが不足する分岐ではエラーを記録してnullを返す。「不足すれば自動的にRAWへ切り替わる」とは解釈しない。

ミッション隣のファイルは、ミッションを共通検索して得た実パスが基準となる。通常のミッション選択やSessionの開始処理に、その実パスの設定元を確認した [R33]。全ミッションの実行や、全地域のタイル列挙は行っていない。

### 地形の設定・材質・テクスチャ

- `TerrainManager.readIniValues` / `init` は `terrain/terrain.ini`、`terrain/biomes.ini` 等の設定を通常のINI経路で読む。季節別の地形材質には `getMaterialResource` を呼ぶ部分がある [R29]。
- 一方、`TextureManager` のバイオーム、環境、水域マスク、スタンプ、植生分布の読込には、`ResourceLoader.loadTextureFromInternal` を使う処理がある。このコルーチンは `Resources.LoadAsync<Texture2D>` を呼び、通常の外部画像検索を行わない [R30]。
- Autogenのモデル・材質にも、INIから得た名前を季節等に応じて変換した後、`Resources.LoadAll<Mesh>`、`Resources.Load<Material>` 等で読む経路がある [R36]。

「地形の画像だからすべて外部PNGの上書き」「材質だからすべて外部INI」という一括した扱いは適切ではない。確認した呼び出し経路の範囲で区別する。

### 配置物

`TerrainManager.loadSceneryObjects` は、ミッション隣の `<mission>_data/objects.ini` と、共通検索の `terrain/objects/objects.ini` を別に読み、配置処理へ渡す [R34]。前者はミッションの実パスに付随し、後者は共通検索の提供順位が適用される。

配置物の定義から呼ばれる `SceneryObjectLoader` も、モデル・材質・画像についてResourceLoaderを使う [R34・R41]。別経路の `PlaceSceneryPrefabs` は、original側の配置定義名の列挙と共通INI検索を組み合わせ、最後にUnity内蔵Prefabを読む [R35]。**一覧の発見元と、同名定義の提供元を解決する範囲が異なる**ため、片方だけを見て判断しない。

`TerrainModConverter.recalculateTerrainMods` はファイルの書込・削除を含む変換用の処理だった。参照索引に直接の呼び出し元はなく、通常MODの読み込み前に必ず実行されるという根拠は得られなかった [R39]。この調査では実行していない。

## 追加調査: AssetBundle経路

`SceneCreator.OnStart` は `Globals._useAssetBundles` によって分岐する。この値は初期値falseで、`OptionsManager.ApplyOptions` が `General.UseAssetBundles` を既定値falseで読み、設定する [R37・R38]。現在のゲームプロセスでの値は取得していない。

その分岐の読込処理は、configのAssetBundle指定に対し、StreamingAssetsのuser側に該当ファイルがあればuser、それ以外はoriginalを使うパスを構築する。`AssetBundleManager` 側は渡されたパスをUnityの `LoadFromFileAsync` へ渡す [R37]。

ここで確認したのは、**設定依存の固定ルートの選択**であり、WorkshopやローカルMODを通常の一覧順に探す処理ではない。パス構築には `file://` を含む指定もあるが、この経路が現環境で正常に読み込むことを実機検証したわけではない。

Bundle内のモデル・材質は、コンテナ内のアセット名で読む。内部アセット同士の衝突や描画結果までを、このMODのファイル重複判定へ追加する必要はない。

## 管理画面の編集中構成を使う制約

`ModMenuViewModel` は `GetSearchDirectories()` から作った一覧を自身の `Directories` に保持する [R01]。確定時にその一覧を `SaveDirectories` へ渡し、`RefreshSearchDirectories` とINIキャッシュ等の無効化へ進む [R02]。

ゲームの検索APIは適用済みの `FileManager.Directories` を参照する。従って、管理画面の未確定のON/OFF・並び替えを反映するには、**管理画面の構成を固定したスナップショットを使う現行の構成を維持する。** 解析目的でグローバルなDirectoriesやキャッシュを変更しない。

`GetFile`、`GetAllMatchingFiles`、`GetFiles`、`GetAllFiles` は、共通検索・列挙の規則を確認する根拠になる [R03～R06]。全ゲームの将来の読み込み要求を返すAPIを用意することは、今回の重複判定の前提ではない。

## 採用した修正と検証

現行の入力スナップショット、ファイル列挙、相対パスごとのグループ化、内容ハッシュ、提供順位と表示を維持する。`ConflictScanner.IsContent` に、正規化した親パスが `ui/backgrounds`、拡張子が `.png` の場合だけを対象外にする条件を追加した。パスと拡張子の比較は大文字・小文字を区別しない。

別名の代替モデルや画像をまとめる機能、INIキーの採用元解析、独自DLLのI/O解析、Unity内部の依存解析は追加しない。既存のINI注意書きはファイル候補の順位を示す説明として維持する。

既存の判定範囲テストを拡張し、修正前には背景PNGが重複として残るため失敗することを確認した。修正後は次を含む28項目が.NET 10と独立したゲーム付属Monoの両方で成功した。

- `ui/backgrounds` 直下のPNGと大文字表記のPNGが重複一覧・件数から外れる。
- サブフォルダのPNG、直下のJPG・JSON、似た名前のフォルダ、他の親フォルダにある画像は引き続き比較される。
- MOD直下の `preview.jpg` と通常のJSONは引き続き比較される。
- 残った重複に対する優先・下位の件数が一致する。

Releaseビルドは警告・エラーとも0件。検証記録はローカル専用の `artifacts/menu-background-filter/verification.json` に保持する。モデル・材質・地形の詳細は静的調査であり、全経路の実機検証を済ませたという意味ではない。
